# Diary: Remove S3

Audio Ad Astra does not need an object store right now. The project template wired in an S3 bucket (via `maragu.dev/glue/s3`), a versitygw S3-compatible server in `docker-compose.yml` for local dev and tests, AWS credentials in `.env.example`, and `s3: true` in the shared CI test workflow. None of it is used by any feature. This task strips all of it out so the project only carries what it uses.

## Step 1: Scope the removal

**Author:** main

### Prompt Context

**Verbatim prompt:** We don't need S3 in this project, delete code, fix CI and docker compose and whatever else you can find, then make a PR

**Interpretation:** Remove every trace of S3 -- Go code, dependencies, local dev infrastructure, env config, CI flags -- and open a pull request with the result.

**Inferred intent:** Keep the project lean. Blob storage may come back later (audio files have to live somewhere), but that is a decision for when there is a concrete need, not template baggage to carry in the meantime.

### What I did

Grepped the repo for `s3`, `aws`, `minio`, `versity`, `bucket`, and `blob`. Found the full footprint:

- `/cmd/app/main.go`: loads AWS config and constructs an `s3.Bucket`, passes it to `service.Setup`.
- `/service/fat.go`: `Setup` takes a `*s3.Bucket` parameter that nothing reads.
- `/docker-compose.yml`: only contains `versitygw` and `versitygw-test` services plus a volume. Nothing else in the file.
- `/Makefile`: `up`, `down`, `test-up`, `test-down` drive the versitygw containers; `test` depends on `test-up`; `clean-all` removes the versitygw volume.
- `/.env.example`: `AWS_*` and `S3_*` variables.
- `/.github/workflows/ci.yml`: `s3: true` input to the shared test workflow.
- `/go.mod`: `aws-sdk-go-v2` modules and `smithy-go` as indirect deps via glue.
- `/.gitignore`: `/.env.docker`, which only the compose services consumed.

No tests reference the bucket. No docs beyond earlier diary entries mention it.

### Why

The lead's job is to make the scope concrete before handing it off. The removal touches Go, Make, compose, env, and CI, so a builder needs the full list rather than a "grep for s3" instruction.

### What worked

A single `grep -rniE` across the repo was enough to find everything; the footprint is small and self-contained.

### What didn't work

Nothing failed at this stage.

### What I learned

The compose file exists solely for S3. Removing S3 means the file is empty, so the decision is to delete `docker-compose.yml` outright and drop the compose-driven Make targets rather than leave an empty file behind. The `.env.docker` gitignore entry goes with it.

### What was tricky

Deciding whether to keep `docker-compose.yml` as a placeholder. No: an empty compose file is a lie about the project's needs.

### What warrants review

The builder's diff, once it lands: `go mod tidy` should drop all `aws-sdk-go-v2` lines, `make test` must work with no Docker running, and the app must start with a `.env` that has no AWS variables.

### Future work

When audio upload lands, blob storage comes back as a deliberate decision recorded in `docs/decisions.md`.

## Step 2: Strip S3 out of the code, infrastructure, config and CI

**Author:** s3-remover

### Prompt Context

**Verbatim prompt (the Goal section of the lead's brief):** "Remove every trace of S3 / object storage from this project. It is template baggage that no feature uses. Blob storage may return later as a deliberate decision, but not now."

The brief then enumerated a nine-point footprint (Go wiring, `docker-compose.yml`, `Makefile`, `/.env.example`, `/.github/workflows/ci.yml`, `/.gitignore`, `go.mod`) and set acceptance criteria: lint clean, `make fmt` producing no diff, `make test` green with no Docker running, `go build ./...` succeeding, and `make watch` starting the app from an S3-free `.env`.

**Interpretation:** Execute the lead's verified footprint, confirm with a repo-wide grep that nothing else remains, and open a PR.

**Inferred intent:** Leave the project carrying only what it uses, so the next person reading `main` or `docker-compose.yml` does not have to work out whether the bucket matters.

### What I did

Started from the test, since `Setup` had one: `/service/fat_internal_test.go` calls `Setup(f, nil, nil, nil)` and walks the `Fat` struct's func fields reflectively to assert every operation got wired. Changing that call to `Setup(f, nil, nil)` produced the red I wanted -- a compile error naming the old signature:

```
service/fat_internal_test.go:32:17: not enough arguments in call to Setup
	have (*Fat, nil, nil)
	want (*Fat, *"maragu.dev/glue/s3".Bucket, *sqlite.Database, *postmark.Sender)
```

Green was dropping the `bucket *s3.Bucket` parameter and the `maragu.dev/glue/s3` import from `/service/fat.go`, and rewording the `Setup` doc comment's closing clause from "bucket and sender are waiting like that" to "sender is waiting like that". Then `/cmd/app/main.go` lost the `aws.LoadDefaultConfig` call, the `s3.NewBucket` construction that read `S3_BUCKET_NAME` and `S3_PATH_STYLE`, both glue imports, and the `bucket` argument at the `service.Setup` call site.

`go mod tidy` then dropped all nineteen `github.com/aws/aws-sdk-go-v2/*` modules plus `github.com/aws/smithy-go` from `/go.mod`, thirty-eight lines from `/go.sum`.

Outside Go: deleted `/docker-compose.yml` (nothing in it but the two versitygw services and their volume) and `/.env.docker.example` (nothing in it but versitygw port numbers); removed `up`, `down`, `test-up` and `test-down` from `/Makefile`, un-hooked `test` from `test-up` and `clean-all` from `down`, and dropped the `docker volume rm $(APP_NAME)_versitygw` line so `clean-all` is just the database files now; removed the four `AWS_*` and two `S3_*` variables from `/.env.example`; removed the `with: s3: true` block from the `test` job in `/.github/workflows/ci.yml`; removed `/.env.docker` from `/.gitignore`.

Three commits, split by layer: the Go and module change, the local dev and test infrastructure, and the CI input.

### Why

The bucket was constructed on every boot and read by nothing, which costs a developer the time it takes to prove that -- and costs CI an S3 server it never talks to. The split into three commits follows the blast radius: a Go reviewer, someone wondering why `docker compose up` stopped existing, and someone reading the CI history are three different readers.

Deleting `.env.docker.example` was not in the brief's list. It only held `VERSITYGW_PORT`, `VERSITYGW_TEST_PORT` and `VERSITYGW_WEBUI_PORT`, and the only consumer was the compose file's `env_file` stanza, so it dies with the compose file; leaving it behind would be a config example for a service that no longer exists.

### What worked

The reflective `TestSetup` turned out to be the ideal entry point. Because it enumerates the `Fat` func fields rather than a hand-written list, changing the `Setup` signature could not quietly unwire an operation -- the test would catch it. And because it passes `nil` for every capability, it did not need to know or care that one of them went away.

The verification pass was uneventful: `make lint` reported `0 issues`, `make fmt` left the tree unchanged on a second run, `go build ./...` succeeded, and `make test` passed every package with `app/service` at 100% coverage.

For the `make watch` check I copied `/.env.example` to `/.env` (zero `AWS`/`S3` matches, by grep) and pointed it at port 8099, since another worktree already held 8080. The app logged a clean start -- database, migrations, job runner, server -- with no AWS lookup anywhere in it, and `curl` got a 200 back. Stopped it and removed the generated `app.db`, `app.log`, `cover.out`, `tailwindcss` and `public/styles/app.css` afterwards.

### What didn't work

I lost three commits to a git mistake and had to redo them. `git rm docker-compose.yml .env.docker.example` staged those deletions early; much later I ran `git add cmd/app/main.go service/... go.mod go.sum` followed by a bare `git commit`, forgetting that a pathspec-less commit takes the *whole index*, not just what I had staged in that breath. The compose deletions rode along into the Go commit:

```
a7aa86e Remove the S3 bucket from the app wiring
 .env.docker.example          |  3 ---
 cmd/app/main.go              | 15 +--------------
 docker-compose.yml           | 34 ----------------------------------
 ...
```

The follow-up `git add docker-compose.yml` then failed with `fatal: pathspec 'docker-compose.yml' did not match any files` -- the file was gone from the worktree *and* already committed, so there was nothing for the pathspec to match. `git reset --mixed 265ae4c` put the working tree back in charge, and re-staging each chunk with `git add -A -- <paths>` (the `-A` matters: plain `git add` on a path whose file no longer exists is the failure above) produced the three clean commits.

Also worth recording: `set -e` did not abort that compound command the way I expected -- the failing `git add` was followed by a failing `git commit` and then a *succeeding* commit of the CI chunk, so I ended up with a partial, mis-partitioned history rather than a clean stop.

### What I learned

Two `AWS`-shaped things survive and should survive. `github.com/minio/sha256-simd` is in `/go.mod` because `go mod why` traces it to `app/lexicons` → indigo's `atproto/atdata` → `go-cid` → `go-multihash/register/miniosha256`: it is a SHA-256 implementation from the MinIO project, nothing to do with object storage. And `/go.sum` keeps two lines for `go.opentelemetry.io/contrib/detectors/aws/lambda`, which `go mod why` traces to Honeycomb's `otel-config-go/otelconfig` *test* binary -- a go.sum-only entry, not in `/go.mod` at all.

`public/favicon.svg` also matches the sweep regex, entirely inside its base64 payload. Stripping the data URI before grepping leaves zero matches.

The best thing I learned came out of self-review rather than the work. This removal is not the first time the S3 wiring was deleted: `/docs/diary/2026-07-31-fat-per-method-wiring.md` records it being taken out of `/cmd/app/main.go` in Step 1 and then deliberately *put back* in Step 3 (`aa88116`), on the reasoning that in a starter template the unused plumbing is a large part of what the reader came for. That diary's "Future work" set out exactly this fork: "If the S3 scaffolding is meant to stay in the template, it needs an operation that uses it; if not, the compose services, CI service containers, Makefile targets and environment variables should go together with a `go mod tidy`." This change is the second branch. It matters that the earlier decision was about template completeness and never about needing object storage, so nothing here contradicts a decision made on the merits -- but the reversal is worth a reviewer knowing about.

The compose file's own history explains why deleting it outright is right rather than lossy: `db11918` replaced MinIO with versitygw (MinIO having dropped its open-source S3 API), and the file has never held anything but those services. `e628d0c` added `s3: true` to both the `test` and `compatibility` CI jobs; `e7275a1` had already removed the `compatibility` job, which is why only one block needed stripping now.

### What was tricky

The `Setup` doc comment. It justifies carrying capabilities no operation wires yet -- "so the first operation to need one finds it already plumbed" -- and named two of them. With `bucket` gone the sentence had to keep its argument while naming one. Saying "sender is waiting like that" holds, but it is worth noticing that the rationale is now load-bearing on a single unused parameter; if `sender` ever gets wired, the whole clause should go rather than be re-pointed at something else.

Verifying "no Docker containers running" was awkward: a `versitygw-test` container is up right now, but it belongs to another worktree's compose project (`merge-upstream-versitygw-test-1`), so stopping it would have broken a concurrent session. I verified by absence instead -- after this change no Go file, test, or config in the repo references S3, AWS, a bucket, or ports 7070/7072 -- which is the stronger claim anyway.

### What warrants review

The `Setup` doc comment in `/service/fat.go`, which is the one piece of prose rather than deletion in the diff. And the two judgement calls beyond the brief: deleting `/.env.docker.example`, and keeping `github.com/minio/sha256-simd` and the `detectors/aws/lambda` go.sum lines on the grounds that neither is object storage.

Behaviourally there is nothing to review: no operation changed, and `app/service` still tests at 100%.

I put the diff through five independent reviewers before handing it back -- one on project conventions and Go doc-comment rules, one scanning the diff cold for breakage, one reading history and the earlier diaries, one mining past PR review comments, and one checking that every code comment still describes reality. None of them found anything to fix. The two useful things they returned were context rather than defects: the `aa88116` history above, and confirmation from PR #2 that the reviewer's standing habit is to question whether a Makefile target is still needed -- which this change satisfies by removing the dead targets outright instead of leaving them orphaned.

### Future work

`Setup` now takes a `sender` that nothing wires. That is deliberate per its doc comment, but it is a single-parameter version of a pattern that argued for itself in the plural. When the first email-sending operation lands, the comment should be revisited rather than edited around.

Blob storage, if it returns for audio uploads, comes back as a decision in `/docs/decisions.md` -- as Step 1 already noted.
